  Veredicto: semiprofesional con ambición real

  No es un juguete, pero tampoco es Burp/Nuclei/Acunetix. Está en el escalón
  "herramienta personal sólida para bug bounty con buena ingeniería". Vamos a
  desgranarlo.

  ---
  Lo que está bien hecho (nivel profesional)

  1. Arquitectura limpia: scanner.py orquesta, módulos independientes (active,
  headers, ssti, paths...), config centralizada, async con aiohttp. Eso es
  ingeniería de verdad.
  2. Anti-FP serio en varios sitios:
    - SQLi: baseline por parámetro con hash MD5 del body limpio — si el error ya
   estaba sin payload, no reporta (active.py:148-164).
    - Blind SQLi: mediana de 3 samples + margen + confirmación con sleep(0)
  (active.py:225-268). Esto es lo que hace SQLMap. Muy bien.
    - SSTI: canary check, baseline, confirmación doble (77=49 + 78=56)
  (ssti.py:50-126). Esto está mejor que muchas herramientas comerciales.
    - XSS: verifica que el payload aparece sin html.escape(), compara conteos
  raw vs escaped (active.py:336-349). Correcto.
    - CORS: distingue * solo vs * + credentials, prueba reflejo con Origin: 
  evil.attacker.com (headers.py:172-222). Profesional.
    - Headers: omite CSP/X-Frame en respuestas JSON (headers.py:23-28), ignora
  cookies de tracking (_ga, _fbp...). Esto es exactamente lo que distingue un
  buen scanner.
    - Paths: soft-404 baseline con 2 UUIDs aleatorios + comparación de
  hash/título (http.py:25-53). Bien.
    - SSRF con OOB: usa interactsh para confirmación real → cero FPs si hay
  callback (active.py:455-507).
  3. IA bien diseñada: pipeline de 3 llamadas (triage masivo + síntesis + deep
  dive) en vez de una por vuln. Inteligente, ahorra rate limit, da contexto
  cruzado para attack chains. Reglas de FP explícitas en el system prompt
  (ai_engine.py:244-262).
  4. JWT offline: detecta alg:none y crackea HS256 con diccionario sin tráfico
  extra.

  ---
  Falsos positivos que sí va a producir

  Aún con las protecciones, te encontrarás con:

  1. Path Traversal sin baseline (active.py:398-407): a diferencia de SSTI/SQLi,
   no compara con baseline. Si la página legítimamente contiene root:x:0:0 en
  algún sitio (docs, tutorial Linux, página de demo), reporta CRITICAL falso.
  Bug claro.
  2. Sensitive paths con HTTP 200 + soft-404 imperfecto: muchos SPAs sirven
  index.html con 200 a todo. El baseline ayuda pero no es infalible — vas a
  reportar /.env como expuesto cuando el body es el index de React. Y la
  severidad sigue siendo CRITICAL CVSS 9.8 sin validar contenido.
  3. JS CVE por nombre de archivo (js_cve.py:64-75): si una CDN sirve
  jquery-3.4.0.min.js, lo marca como vulnerable — pero 3.4.x recibió parches de
  seguridad en 3.5.0. La firma 3\.[0-4]\. mete a 3.5.x dentro si el regex se
  interpreta mal. Y solo mira los primeros 4096 bytes del JS minified.
  4. Open redirect a "login,admin,auth" en admin_panels.py:153: cualquier 302 a
  /login te genera un hallazgo. WordPress, Symfony, Rails todos hacen esto en
  cada ruta protegida.
  5. EOL signatures por substring (config.py:124-140): "IIS/5" matchea contra
  "IIS/5.1", "IIS/5.0" — bien — pero también contra cualquier banner que
  mencione esa cadena. Versiones modificadas/proxificadas pueden generar FPs.
  6. YAML engine sin extractors: solo tiene 1 template (env-exposure.yaml).
  Cualquier coincidencia de palabra en body devuelve la severidad cruda del
  template. No hay validación de status code.
  7. CSP unsafe-inline con nonce/hash presente (headers.py:86-107): si la CSP
  usa 'nonce-...' o 'strict-dynamic' junto a 'unsafe-inline' (configuración
  correcta moderna donde unsafe-inline actúa como fallback), igualmente reporta
  HIGH. Falso positivo.
  8. CORS check arbitrario: headers.py:204 envía Origin: evil.attacker.com UNA
  sola vez. Si el servidor refleja porque está en whitelist + el dominio
  resuelve a tu petición, FP. Falta probar con un origen canónico aleatorio para
   confirmar reflexión.
  9. Bounty estimator te dará rangos USD que solo sirven como marketing. No los
  presentes a un cliente.

  Resumen: la base estática (SQLi, XSS, SSTI, blind SQLi, CORS, headers) es
  honestamente buena. Las áreas débiles son path traversal, sensitive paths, JS 
  CVE database y YAML engine.

  ---
  Mejoras prioritarias (ordenadas por ROI)

  Top 5 (las que te darán mejor herramienta YA)

  1. Path Traversal con baseline (modules/active.py:388)
    - Hacer una petición con valor benigno antes del payload, comparar hash.
  Replicar el patrón de SSTI/SQLi. ~15 líneas.
  2. Validación de contenido en SENSITIVE_PATHS (modules/paths.py:55)
    - Para .env: requerir que el body contenga = y \n y NO contenga
  <html/<body>.
    - Para .git/config: requerir [core] o [remote.
    - Para wp-config.php: si devuelve PHP source es expuesto, si devuelve HTML
  render es WP normal.
    - Sin esto vas a reportar muchos CRITICAL falsos en SPAs.
  3. JS CVE: rango de versión real (modules/js_cve.py)
    - Sustituir regex jquery[/-]3\.[0-4]\. por parsing semver y comparación
  version < 3.5.0. Las expresiones actuales son frágiles.
    - Considerar usar
  https://github.com/RetireJS/retire.js/blob/master/repository/jsrepository.json
   en vez de mantener JS_CVE_DB a mano.
  4. CSP context-aware (modules/headers.py:86)
    - Si la CSP contiene 'nonce- o 'strict-dynamic', no reportar unsafe-inline
  (es fallback intencional según spec CSP 3).
    - Soft-fail similar para * cuando aparece sólo en img-src/media-src.
  5. CORS confirmación doble
    - Probar con 2 orígenes distintos aleatorios. Solo reportar si ambos se
  reflejan. Elimina el FP de "el servidor incluye un eco del Origin por debug".

  Mejoras de medio plazo

  6. Dejar de meter passwords/API keys por stdin en main.py:83
    - Cambiar a getpass o lectura de variable de entorno. Tal como está, la API
  key queda en el historial del terminal y en .ai_config.json en texto plano (¡y
   ya lo guardas en .ai_config.json!).
  7. Persistencia de sesión real para autenticación
    - Solo se pasan headers estáticos. No hay CSRF token re-fetch, no hay
  re-login. Para apps reales necesitas un manejador de sesión con
  aiohttp.ClientSession autenticada.
  8. YAML templates de verdad
    - Solo tienes 1 template. Adoptar el formato completo de Nuclei (extractors,
   matchers OR/AND, dsl) y cargar el repo público de Nuclei como subset, o
  eliminar el módulo. Como está, es decorativo.
  9. Manejo de errores en _chat (ai_engine.py:160-163)
    - Hace traceback.print_exc() dentro del retry loop. En producción ensucia la
   salida y no clasifica el error (DNS, TLS, auth, 5xx).
  10. CVSS estático en lugar de calculado (utils/vuln.py:25)
    - Tienes severity_from_cvss definido pero usas valores fijos hardcoded.
  Calcula CVSS vectorial real cuando el AI engine lo provee (cvss_vector ya está
   en el deep_dive).

  Mejoras estratégicas

  11. WAF bypass: el stealth mode rota UA pero no rota IP. Sin proxy chain
  (Tor/proxy pool) un WAF mediano te bloquea en 10 minutos. Considera
  integración con proxies SOCKS o burlas más sofisticadas (encoding chains,
  comentarios MySQL, etc).
  12. Reporting: PDF/HTML está bien, pero falta exportar a formatos de
  plataformas (HackerOne markdown, Bugcrowd template). Sería diferenciador.
  13. Modo "verify" pasivo: una opción para confirmar manualmente cada hallazgo
  antes de reportarlo, con interfaz CLI. Esto es lo que hacen los pros antes de
  submitir.
  14. Tests: el repo no tiene tests/. Sin unit tests es imposible refactor
  seguro y los FPs nuevos se cuelan en cada commit.
  15. Crawler limitado: 100 páginas, depth 2. Para apps reales necesitas
  integración con headless browser (Playwright) para descubrir endpoints de SPA,
   AJAX, WebSockets.
